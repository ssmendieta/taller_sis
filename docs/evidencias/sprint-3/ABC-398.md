## 5. Hallazgos

1. **Las unidades recuperadas no llegan a Lotes ni al cierre.** El reproceso
   suma las recuperadas a las conformes solo en sus propios totales (CA-03 se
   cumple ahí). Sin embargo:
   - `LotesService` limita los lotes con la suma de resultados `CONFORME`;
   - `CierreProduccionService` cierra con `resultados_conformes`.

   En el ejemplo del CA, las 2 recuperadas no se pueden asignar a un lote, y por
   eso no pueden salir a Logística. El reporte de Producción (ABC-336) muestra
   reprocesadas, recuperadas y descartadas aparte. Se sugiere al equipo de
   ABC-394 decidir si Lotes debe usar el saldo derivado (conformes +
   recuperadas), para cumplir el valor *"recuperar producto"*.
2. **La base acepta `cantidad_procesada = 0`.** El CHECK de ABC-395 usa `>= 0`. La
   API lo impide (`@Min(0.0001)` en el DTO), así que CA-01 se cumple. Un `> 0` en
   la base daría la misma protección a cualquier otra vía de escritura.

## 6. Qué no acredita esta evidencia

- **No usa PostgreSQL real.** El bloqueo, el rollback y el SQL se probaron con una
  base simulada. La suite real `reproceso.persistencia.spec.ts` existe e incluye
  concurrencia. Según el README de ABC-396 la ejecutó Andrea con PGlite; en esta
  verificación se omitió porque no había base disponible.
- La ejecución en el entorno Docker de ABC-399 queda pendiente.
