Se agrupan controlador, servicio, publicador y consumidor dentro del participante
de su microservicio para mantener cinco participantes y facilitar la lectura.
La validación se simplifica en el dibujo: las comprobaciones que necesitan datos
persistidos se realizan dentro de la transacción del procesador. Un error
permanente en esa transacción causa rollback y ACK con registro del descarte.

## Reglas que deben explicarse en la demo

- `eventId` identifica un mensaje lógico; `correlationId` une la conversación;
  `requestEventId` refiere el evento original; `messageId` lo asigna Google a
  cada publicación física. En los dibujos, A y B son eventId distintos y C es
  la correlación compartida. En ejecución se usan UUID.
- Una confirmación perdida puede causar otra publicación física. Los reintentos
  conservan el payload y el eventId; el inbox evita reaplicar el efecto.
- `PUBLICADO` acredita confirmación del broker, no que otro SI ya aplicó el
  negocio. Contabilidad responde `RECIBIDO` o `RECHAZADO`. Inventarios responde
  `ACEPTADA` o `RECHAZADA`.
- Repetir el mismo eventId con un cuerpo diferente es un conflicto permanente,
  no un duplicado válido. La primera respuesta final prevalece; otra respuesta
  posterior queda registrada como `IGNORADO`.
- Si un trabajador cae antes de liberar un registro, el vencimiento del lease
  permite reclamarlo de nuevo. Si cae después de un commit de inbox y antes
  del ACK, la reentrega se reconoce como duplicada.
- El cierre envía cantidades, consumos y el costo base en BOB calculado con el
  catálogo de materiales (ABC-345). Solo hay total cuando todos los consumos
  tienen precio válido y unidad compatible: `COMPLETO`; en otro caso se indica
  `PARCIAL` o `PENDIENTE` sin inventar un total. El costo queda congelado en el
  payload del outbox, no modifica el snapshot histórico. El asiento contable
  externo y los cambios internos de stock de Inventarios no se inventan en
  los diagramas.
- La consulta de materiales previa al inicio es otro flujo, ABC-70, ya
  documentado en la secuencia `06-produccion-inicio-orden.mmd` de ABC-407.

## Vista de despliegue

Mermaid representa nodos con estereotipos UML de dispositivo, contenedor,
servicio administrado y volumen. Es una vista lógica de la configuración
Compose, no una captura de Docker ni una afirmación de despliegue cloud.
El navegador descarga el frontend y llama al gateway directamente. El frontend
sirve Vite preview, no Nginx. PostgreSQL es un contenedor con tres bases lógicas
y un volumen persistente; los puertos del dibujo son los predeterminados.
El mapeo local de PostgreSQL puede variar, por ejemplo `55432:5432`.

El Pub/Sub administrado se utiliza cuando están habilitadas las integraciones
y configurados sus recursos y credenciales. El override local sin GCP apaga esas
flechas. El emulador opcional no forma parte de esta vista de Google Cloud.
El Compose base actualizado monta la cuenta de servicio de solo lectura en
Producción y Logística. El archivo real y los permisos aún deben existir en
el equipo que ejecute la demo. El topic puede compartirse; las suscripciones
de consumidores con contratos distintos deben estar separadas o usar un
enrutador común. Si se activa la misma suscripción en ambos consumidores,
compiten por las entregas y uno puede confirmar un evento destinado al otro.
El fallback de ABC-402 a `PUBSUB_SUBSCRIPTION_ID` debe revisarse antes de
activar simultáneamente los consumidores.

## Validación y publicación

Las tres fuentes se validan y renderizan con Mermaid 11.17.2 y la configuración
`docs/diagramas/sprint-3/mermaid-integraciones.config.json`. Se generan SVG,
PNG a escala 2 y PDF de una página con la imagen completa. Se utiliza un DOM
virtual para SVG, resvg para PNG y ReportLab para PDF. El comando de Mermaid
CLI 11.4.2 del README es una alternativa para regenerar desde Windows.
Las exportaciones se revisan
visualmente y se comprueba que no haya enlaces locales rotos ni errores de
espacios en el diff.

El cambio es documental: no modifica servicios, dependencias del proyecto,
usuarios, credenciales, migraciones ni datos. No se repiten suites de negocio
sin cambios de código. La publicación se realiza con la cuenta de Andrea y el identificador
ABC-406; después de fusionar se enlaza en Jira junto con los archivos exportados. Esta entrega no cierra ABC-347 ni ABC-403: requieren validación de
mensajería real y del entorno Docker respectivamente.
