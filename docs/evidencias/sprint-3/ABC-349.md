# ABC-349 — Reintento y pruebas del cierre contable

HU principal: ABC-114. Rama `ramagemina`. Ejecución local del 03/11/2026 con
PostgreSQL 15 (`taller_postgres`) y el **emulador** de Pub/Sub
(`taller_pubsub_emulator`). **Todo lo de este documento es prueba local/simulada**:
no se publicó ni consumió nada en Google Cloud Pub/Sub real.

> RECIBIDO significa recepción administrativa del cierre por Contabilidad; **no**
> equivale a un asiento contable aprobado.

## 1. Suites con PostgreSQL real

```powershell
cd services/produccion-service
$env:CONTABILIDAD_DB_REAL='1'; $env:CIERRE_DB_REAL='1'; $env:OUTBOX_DB_REAL='1'; $env:INBOX_DB_REAL='1'
$env:DB_DATABASE='produccion_db'
npx jest --runInBand src/integraciones/inbox src/cierre-produccion src/integraciones/outbox src/integraciones/integraciones
```

Resultado: **15 suites, 158 pruebas aprobadas, 0 fallidas**. Cada suite crea y
borra su propio esquema aislado; no modifica los datos de la base habitual.

Casos agregados por ABC-349 en `resultado-contable.persistencia.spec.ts`:

| Caso | Resultado comprobado |
| --- | --- |
| Mismo `eventId` con contenido contradictorio | Rechazado ("contenido diferente"); el cierre sigue RECIBIDO, 1 fila de inbox |
| Resultado no correlacionado (apunta a otro cierre) | Rechazado; ambos cierres siguen PENDIENTE, sin inbox |
| Base caída durante el procesamiento | NACK sin efectos; tras recuperar, la redelivery aplica RECIBIDO una sola vez |
| Dos entregas simultáneas del mismo resultado | Una PROCESADO y una DUPLICADO; 1 fila de inbox |

Casos existentes que siguen aprobados con base real: éxito RECIBIDO, RECHAZADO
final con resultado tardío ignorado, mensaje inválido revertido, interrupción
después del commit sin doble efecto, outbox con broker caído y reintento
administrativo (ABC-121/242/267/275).

## 2. Recorrido local con emulador y simulador de Contabilidad

Configuración según `docs/integraciones/contabilidad-local-e2e.md`
(topic de ida `taller-produccion-cerrada-local`, vuelta
`taller-contabilidad-resultados-local`).

| # | Paso | Evidencia |
| --- | --- | --- |
| 1 | Supervisor intenta `POST /cierres-produccion` | HTTP 403, sin filas nuevas |
| 2 | Encargado de Producción prepara cierre v2 de ORD-2026-00002 | HTTP 201, cierre `2`, estado contable PENDIENTE |
| 3 | Outbox publica `ProduccionCerrada.v1` | `eventos_outbox` PUBLICADO, messageId `9` (emulador) |
| 4 | Simulador con `CONTABILIDAD_SIMULATOR_CRASH_AFTER_SAVE_ONCE=true` | `REQUEST_STORED` → `CRASH_AFTER_SAVE`, código 86; cierre sigue PENDIENTE |
| 5 | Simulador reiniciado normal | Reenvía la respuesta pendiente; Producción registra `RESULTADO_CONTABLE_RECIBIDO`, messageId `10`, eventId `31e1cf35-df22-47a0-a6d2-65fa285afe89` |
| 6 | Estado final | cierre `2` RECIBIDO; cierre `1` sin cambios (PENDIENTE); 1 fila de inbox |
| 7 | Se republica el mismo `ProduccionCerrada.v1` (messageId `11`) | Journal del simulador con un solo `RECEIVED`; Producción sigue con 1 fila de inbox y estado RECIBIDO |
