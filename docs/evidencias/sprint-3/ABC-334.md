# ABC-334 · Detalle cronológico de eventos de producción

La línea temporal se abre desde el listado de ABC-333 mediante **Ver cronología**.
Integra estados, avances, calidad, mermas, observaciones, incidencias, lotes y
reprocesos de una sola orden. Incluye permisos, error recuperable, orden
inexistente, estado vacío y descarte de respuestas tardías al navegar entre
órdenes. La API mantiene el orden cronológico y la precisión de las cantidades.

Se corrigieron los estados de filtro incorporados por ABC-333 para usar el
glosario compartido. PENDIENTE, PLANIFICADA, EN_PRODUCCION, FINALIZADA y CANCELADA
coinciden con la API existente.

## Validación ejecutada

- 54 pruebas backend aprobadas, incluidas 16 de persistencia sobre PostgreSQL
  nativo aislado. Las migraciones del proyecto se aplicaron en un esquema de
  prueba. Se verificaron fuentes, aislamiento entre órdenes, precisión,
  desempates estables y ejecución en una transacción READ ONLY.
- 21 pruebas frontend aprobadas del listado y de la nueva cronología, con
  respuestas simuladas. Cubren acceso desde AppRoutes, permisos, reintento,
  sesión expirada, datos vacíos y respuestas tardías.
- Integración con Gateway, Auth y Producción reales, cada servicio conectado a
  sus bases PostgreSQL de prueba. Comprobados 200, 400, 401, 403 y 404.
- Recorrido React con React Test Renderer contra ese gateway. Se abrió el
  listado, se siguió **Ver cronología** y aparecieron los nueve eventos de la
  orden objetivo, sin el evento de otra orden.
- Compilación de Producción y frontend correcta. No se hizo inspección visual
  de la pantalla en un navegador.

## Reproducción

Desde `services/produccion-service`, con PostgreSQL de prueba configurado:

```powershell
$env:HISTORIAL_DB_REAL='1'
npm test -- --runInBand src/historial
npm run build
```

Desde `frontend`:

```powershell
node --test scripts/historial-produccion.test.mjs scripts/cronologia-orden.test.mjs
npm run build
```

El contrato está en `services/produccion-service/src/historial/README.md`.
