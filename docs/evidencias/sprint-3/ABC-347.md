# ABC-347 · Publicación idempotente de ProduccionCerrada.v1

El cierre y su evento se guardan juntos. El publicador reintenta el mismo
registro del outbox, conservando cuerpo y atributos. Ante una confirmación
ambigua el broker puede recibir más de una entrega; el consumidor deduplica
por `eventId`. El estado `PUBLICADO` y su `messageId` acreditan la entrega al
broker. `RECIBIDO` y `RECHAZADO` son respuestas de Contabilidad.

## Evidencia local

Doce pruebas de outbox y publicación aprobadas. El caso ABC-347 simula perder
la confirmación inicial y verifica reintento byte a byte, `eventId` y
`correlationId` iguales, persistencia del `messageId` simulado y cero
publicaciones adicionales tras la confirmación. La compilación pasó.

```powershell
npm test -- --runInBand src/integraciones/outbox/outbox-publicador.service.spec.ts src/integraciones/pubsub/pubsub-publisher.service.spec.ts
npm run build
```

## Pendiente para cerrar la subtarea

Validar con el proyecto y tópico de prueba de Google Pub/Sub provisionados
para el equipo. Desde Producción, cerrar una orden de prueba, localizar el
registro `PUBLICACION_OUTBOX_CONFIRMADA` y contrastar en el outbox el mismo
`eventId`, `correlationId` y `messageId`. Adjuntar fecha y hora, cuerpo de la
orden de prueba y `messageId` de Google. La configuración está en
[Pub/Sub por entorno](../../integraciones/pubsub-entorno.md).
